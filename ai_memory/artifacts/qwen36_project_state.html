The headline — one trial killed 128, and we had predicted it

1229488 failed with ray.exceptions.WorkerCrashedError, which is a red herring: the raylet lines are teardown consequence. The cause is three log lines: 

05:29:11 DEBUG    _classify_exception:1296  Exception AddTestsDirError not in config,

05:29:11 WARNING  _process_trial_result     failed with Harbor exception:
                                           Failed to add tests directory to <env>

AddTestsDirError matched neither mask_exceptions nor passthrough_exceptions, fell through to default_error_treatment: mask, and because mask means infrastructure under fail_on_infrastructure_error: true, it aborted all 128 trajectories. It hit two trials on two different coordinators within one second — a correlated JURECA-side blip, so every run was equally exposed.

The uncomfortable part: gotchas.md already said "mask = infrastructure ⇒ ABORTS the whole batch… any new exception subclass must be enumerated or it silently falls through." It was documented, understood, and unmitigated.

Why the fix is mask + no-abort, and explicitly NOT passthrough

fail_on_infrastructure_error is now false, and AddTestsDirError is enumerated in mask_exceptions. The reason true existed — stop infrastructure failures becoming training signal — is already served by default_error_treatment: mask: a masked trial is excluded from the RLOO baseline and gets advantage 0, so it cannot pollute the gradient. All true added was making one bad trial fatal to 128.

Putting it in passthrough_exceptions would have been actively harmful. Passthrough scores the trial as a real trajectory — a 0. On a task that otherwise scores 1, a spurious 0 fabricates within-group variance, which would make a zero-gradient run look like it had learning signal. That is the one failure mode worse than aborting.

The cost of false, stated plainly: infrastructure failures now degrade quietly instead of shouting. If enough trials mask out, groups fall under rloo_n_min_group_size and contribute zero advantage while still presenting as a valid batch. Per-run exception counts have to be watched.

How the 600-second cap hid

Four layers, each individually reasonable. The outer guard could only ever fire if it were shorter than the inner one, and it wasn't:

  1. trial.py computes the agent timeout as 1800 s from override_timeout_sec. Correct.
  2. _run_agent_phase() wraps the agent in asyncio.wait_for(..., timeout=1800) — an outer guard.
  3. opencode.py calls exec_as_agent() without passing that timeout. This is the gap.
  4. apptainer.py falls back: effective_timeout = timeout_sec or 600, and sends 600 to the worker.
  5. The worker kills at 600 s → return_code -1 → NonZeroAgentExitCodeError. The outer guard never gets to fire.
Fourth instance of the same bug class

A key that is accepted, deep-merged, written to disk, and then ignored by its consumer — after strict_json_parser, compaction.reserved, and store_all_messages. Verifying that a key reaches the materialized config proves nothing. Only behaviour does.

A related correction: NonZeroAgentExitCodeError was recorded as “the norm for OpenCode.” It was not — it was the timeout kill. Reclassifying it to passthrough was still right, but the wrong diagnosis hid the real defect for a day.

Initialization — the model, and why there is no conversion step

Exact origin is Qwen/Qwen3.6-35B-A3B at revision 995ad96eacd98c81ed38be0c5b274b04031597b0, staged verbatim from the hub to /e/scratch/reformo/lee27/models/Qwen3.6-35B-A3B/995ad96e…. The revision is pinned in the directory name, and the preflight asserts model.name == expected_revision — there is no generated provenance file to drift. Policy, reference, both rollout engines and both eval arms resolve to that one path, so nothing about format can confound the measured delta.

The published checkpoint is a multimodal shell (Qwen3_5MoeForConditionalGeneration). We train only the text tower. The mechanism that strips it is the part worth knowing precisely:

SKYRL_QWEN3_5_VLM_UNWRAP=1 (SkyRL's default) makes the unwrap happen in memory. Per skyrl_train/models/qwen3_5_vlm.py it is a pure reference re-point of already-loaded submodules — text keys map 1:1, 0 missing / 0 extra. The same flag gates map_text_name_to_vlm_engine, so the trainer's parameter names and the rollout engines' names stay in lockstep during weight sync. Never set this to 0 — that was the old design, which required an on-disk pre-unwrapped checkpoint that no longer exists.

Cost of unwrapping on every load: ~2.4 GiB of extra read, 3.6%, on data being streamed anyway, roughly ten times per job. The rejected alternative was a second permanent 67 GB artifact plus a conversion job and script.

The one real cost, named honestly

Rollout engines instantiate the full shell too, so ~0.8 GiB of vision weights sits resident per engine, unused. Under 1% of a 96 GB GH200, but it comes out of KV-cache headroom. Watch it only if KV pressure ever becomes binding.

Downstream consequence, deferred to publishing: the export will be text-only, so it is not a drop-in replacement for the base model. Re-attaching later is ~40 lines given the 1:1 key mapping.

GDN and FlashQLA — the architecture, and the kernel it demands

These are the two things that arrived with the model switch, and they are unrelated to precision. GDN is an architecture; FlashQLA is the kernel that makes it trainable at our prompt length.

GDN — Gated DeltaNet

A linear-attention layer. Softmax attention compares every token to every other, so cost grows with the square of sequence length. GDN carries a fixed-size recurrent state updated by a gated delta rule, so cost grows linearly.

Qwen3.6 is hybrid: three GDN layers per four-layer block, so one layer in four is full attention. Most of linear attention's efficiency, some exact-recall capacity retained.

The signature lives on config.text_config, not the top-level config — because we deliberately stage the shell. The preflight asserts linear_conv_kernel_dim and a layer_types list containing a linear entry, because without them SkyRL's unwrap probe never fires and FlashQLA is silently skipped.

FlashQLA 0.1.2 — the kernel

The delta-rule update is inherently sequential, so the Transformers pure-Torch fallback walks the recurrence step by step. Tolerable on short prompts, prohibitive at 28,672 tokens. A fused, chunked kernel is mandatory.

Two constraints make it awkward: it must be built for ARM64 (GH200 is aarch64), and it must support the backward pass, since this is training.

MarinSkyRL binds it to Qwen3_5MoeGatedDeltaNet and fails loudly if the kernel is absent or unused — SKYRL_GDN_FLASHQLA_REQUIRED=1. You cannot silently fall back to the slow path and mistake it for a hung job.

The kernel ships as a fully pinned dependency layer at /e/scratch/reformo/lee27/pydeps/qwen36-flashqla-0.1.2, prepended to PYTHONPATH. The preflight reads its manifest and then reads the installed distributions on that path and requires exact equality with five versions — it does not trust a build log line.

The consequence chain nobody expects

One flag cascades into four required settings. This is the single highest-value thing to internalize about our trainer configuration:

  1. colocate_all: false is forced by the falsified-colocation decision.
  2. main_tbench.get_trainer() keys only on that flag: FullyAsyncRayPPOTrainer if colocate_all is False else RayPPOTrainer. There is no separate opt-in — the fully-async trainer is not optional.
  3. Its constraint set becomes hard requirements: train_batch_size == policy_mini_batch_size, dynamic_sampling is None, async_engine: true, and batched: false — batched: true dies with AssertionError: batched is not supported for fully async training after all eight engines have already loaded.
  4. num_parallel_generation_workers defaults to 768. Throughput is capped by the engine working set (16 groups), so a large pool adds nothing and accumulates a stale backlog that pins head-node memory. Set to the floor: 32.
  5. Fully-async training is off-policy by up to max_staleness_steps. That changes what the experiment is, not just its speed. use_tis: true with tis_imp_ratio_cap: 2.0 is the correct mitigation and stays on.

Why TIS and not router replay: the measured generator↔trainer gap was log_ratio_abs_mean ≈ 0.030 nats (importance ratio ≈ 1.009) with a routing tail of 0.035% capped. R3 would recover approximately nothing here. Revisit only for long-context, larger-MoE, or genuinely high-staleness regimes.

Where a rollout's reward comes from

The whole cross-cluster architecture exists to answer one question: where does the throwaway Linux box come from that grades each rollout? Every constraint below follows from that.

Why not Daytona

It's a cloud API and JSC compute nodes have no internet. Every rollout failed — that is what killed the 07-29 run.

Why not Docker

No root on a shared HPC cluster. Apptainer runs unprivileged from a single-file .sif.

Why two clusters

SWE-Bench SIFs are x86_64; Jupiter's GH200s are aarch64. And Jupiter has no CPU-only partition — local sandboxes would burn GH200s running pytest.

Why a reverse tunnel

Jupiter compute can't reach JURECA, and JURECA can't reach Jupiter at all. But compute can reach a Jupiter login node internally, and JURECA's login node can dial out.

Questions worth asking about the sandbox layer

The concurrency and isolation story is the least documented part of the stack and the part most likely to surprise you. Answers below are read out of harbor/environments/apptainer/{server,worker}.py and the live allocation, not inferred.

Q1How many rollouts can actually be in flight at once — and which number is the real ceiling?

Four different limits stack, and they are deliberately not equal. The binding one for token throughput is 16; the binding one for sandboxes is 32.
  • 32Worker slots. 2 JURECA nodes × WORKERS_PER_NODE=16. One Apptainer instance per worker.
  • 32Harbor trial concurrency — n_concurrent_trials: 32. Deliberately matched to worker slots.
  • 32Rollouts in the smoke step — 8 prompts × 4 samples. So the step is sized to fill the sandbox fleet exactly once.
  • 16Concurrent generation groups — 8 engines × max_num_seqs 8 ÷ 4 samples. This is the token-throughput ceiling.
  • 8Concurrent instance starts per node — BRIDGE_START_CONCURRENCY=8. A throttle on setup only, not on running work.

The apparent mismatch — 32 sandboxes for 16 servable groups — is correct and necessary. A trial holds its sandbox for the entire episode, including all the time it spends waiting on the model to produce the next command. An idle container costs a process and some page cache; a queued trial that cannot get a sandbox costs wall-clock. So the sandbox pool is provisioned to the rollout count, and the engines throttle generation underneath it.

Q2How many nodes does one task get? And if a node has 256 CPUs, why only 16 tasks on it?

A task gets 2 CPUs of one node — not a node. And the node is only ~12% subscribed, because the limit is neither cores nor memory.

A JURECA dc-cpu node is 256 logical CPUs and ~515 GB RAM. Our allocation takes --cpus-per-task=128 and --mem=0 (the whole node) on each of 2 nodes. Each trial is capped at override_cpus: 2 and override_memory_mb: 4096. So 16 workers consume 32 of 256 CPUs and 64 of 515 GB.

The real constraint is Apptainer's setuid starter. From the worker source: "the suid-starter overloads when too many fakeroot+overlay.img creations run in parallel (seen at >~16 concurrent starts: starter-suid exit 255)". That is why 16 is the worker count and why starts — but not exec or stop — are throttled to 8 by a semaphore. The ceiling is an image-instantiation bottleneck, not a resource one, which also means adding CPU nodes scales the fleet linearly while raising workers-per-node does not.

Zero GPU nodes are involved in grading. That is the entire point of the two-cluster split: pytest runs on free CPU while the GH200s stay on tokens.

Q3If 3,328 tasks share only 7 images, how does each trial get its own filesystem — and how does state not leak between them?

The SIF is immutable and shared. Every writable byte a trial produces lives in a per-trial ext3 overlay image plus a set of per-trial bind mounts, both on node-local disk.

Per environment the worker creates a unique env_id, an instance named hb_<env_id>, and a staging directory via mkdtemp under the node-local staging base. Inside that staging directory it runs apptainer overlay create --size 4096 overlay.img and attaches it with --overlay. That ext3 image is the 4096 MB storage limit — it is a filesystem size, not a cgroup quota.

On top of that, each instance gets its own read-write binds — /workspace, /tests, /setup_files, /logs/agent, /logs/verifier, /tmp, and the Dockerfile's WORKDIR — plus read-only binds for the static agent tools into /usr/local/bin. Isolation is Apptainer's own mount namespace, so two trials from the same SIF see different roots for every path either of them can write.

One implementation detail worth carrying: it must be an overlay image file, not a directory. In setuid mode Apptainer rejects a directory overlay — "only root user can use sandbox as overlay in setuid mode" — and --writable-tmpfs would cap the writable layer at RAM. The image file is the only option that gives an unprivileged, sized, writable layer.

Q4When the model emits a command, how does the system know which of the 32 containers to run it in — across two clusters and a tunnel?

Sticky routing on env_id. The first job for an environment is claimable by anyone; every job after it is pinned to the worker that claimed it.

The bridge keeps _envs (env_id → env info), one general _job_queue, and _worker_queues (worker_id → deque). POST /env/create mints an env_id and enqueues a START job on the general queue. Whichever worker polls GET /worker/get_job first claims it and becomes that environment's owner. From then on, every exec, upload, download and stop for that env_id is routed to that worker's queue.

This is forced, not stylistic: the instance and its overlay image exist only on one node's local disk. No other worker can apptainer exec instance://hb_<env_id> against it. The trainer never addresses a node — it addresses an env_id, and affinity is the bridge's problem.

Q5128 concurrent sandboxes over one SSH tunnel — why isn't the tunnel the bottleneck?

Because workers never poll it. One dispatcher per node polls on behalf of its 16 workers, so tunnel traffic scales with nodes, not sandboxes.

The co-lead's design note says it plainly: "Only 32 dispatchers poll through tunnel (not 512 workers)." At the 128-way scale test, eight nodes × 16 workers ran through exactly eight pollers. The measured result: 128/128 oracle rollouts completed in 96 s with zero exceptions, retries, cancellations, or connection errors.

Live counters put the polling cost in perspective: 40,165 worker polls for 1,442 jobs, ~28 polls per job. That ratio is what you pay for a poll-based design, and it is affordable precisely because it is the dispatcher paying it.

Q6What happens to a trial if its worker or the tunnel dies mid-episode?

By design it becomes a named infrastructure exception that is masked, never scored zero. Recovery, as distinct from correct failure, is unproven — that is gate 5.

Sticky routing means an environment is pinned to one node, so a lost worker strands that environment's queued jobs. The intended path is that this surfaces as BridgeOutageError / BridgeOperationTimeoutError, lands in mask_exceptions, and is therefore excluded from the GRPO baseline rather than entering it as reward 0. Bridge errors are deliberately not subclasses of agent TimeoutError so the two can never be conflated.

What has actually been measured is the healthy path: 1,442/1,442 jobs, zero job errors, and 101 environments created and reaped. A forced disconnect has never been run. Gate 5 is exactly that test — break the ControlMaster and forward at ServerAliveInterval=1 / ServerAliveCountMax=1, confirm failure is loud and workers plus queued work recover, then restore conservative production keepalives. Until then, treat recovery as a design intention.

Q7Why does the smoke request only 2 CPU nodes when the scale test used 8?

Because the smoke needs exactly 32 slots, and the 16-node combined JSC ceiling has to cover 6 Jupiter GPU nodes too.

6 + 2 = 8 of 16. The 32 rollouts of a one-step smoke fit precisely in 2 × 16 worker slots, so more CPU nodes would sit idle while consuming budget that the GPU side may need. Promotion to 50 steps is where the worker fleet scales back up — and where the auto-chain matters for the first time, since it has never actually crossed a walltime boundary (MAX_CHAIN=0 in every recorded smoke). It is off the critical path today only because workers now request the 24 h maximum, which outlasts the run.

Reward integrity — the most dangerous class of bug we have

Under GRPO, all-zero reward means zero advantage variance means no gradient. A run can therefore execute flawlessly end to end — weight sync, generation, logprobs, advantages, policy train — and report nothing wrong while learning nothing. Job 1087425 did exactly that: avg_raw_reward: 0.0, zero_rewards: 1.0, 128/128 rollouts dead on an unreachable cloud API.

Corrected 2026-07-31 — the earlier explanation of this was wrong

The old account blamed mask_exceptions plus default_error_treatment: zero for absorbing connection failures. That is not what the code does. The structural hazard that remains

Matching is still name-based. Any new exception subclass must be enumerated by hand or it silently falls through to the default. Fail-loud config limits the damage; it does not remove the hazard. Practical rule: always grep an RL log for Network is unreachable and connection errors before believing a low reward. avg_raw_reward: 0.0 is far more often infrastructure than capability.

The launch wrapper enforces the same principle before Slurm ever sees the job: it curls $APPTAINER_BRIDGE_URL/status and refuses to submit on failure, with the comment "A disconnected bridge can otherwise masquerade as zero reward."

And a data-shaped version of the same risk

The co-lead reports raw r2egym collapses with zero reward; she trains on a model-specific learnable band (0 < pass@8 < 1 → 740 train + 100 held out). Our config trains on all 3,328 — the configuration already known to fail for her. The band is parked by operator decision; do not re-litigate it. But keep the consequence in mind when reading gate 4: a flat reward curve may be the data, not the sandboxes. If variance is zero, stop and report rather than silently promoting.

Failure modes worth memorizing

Each of these cost more than ten minutes, and most of them look like something else. The silent ones are the expensive ones.

Silent flash_attn: false is never a one-line change

Turning flash attention off does not fall back to SDPA. resolve_attn_implementation() maps attn_backend: auto plus use_flash_attention_2=False to eager. At 28,672-token prompts eager attention is quadratic-memory and glacial — a run that "works" but is unusable, with no error anywhere.

There is also a loud half: use_sample_packing defaults to true and is implemented only on the flash-attn-2 varlen path, so it asserts at init_model.

Fix The trio, always together: flash_attn: false + attn_backend: sdpa + use_sample_packing: false. Packing costs nothing at micro_train_batch_size_per_gpu: 1 anyway.

Silent A parquet as train_data yields zero tasks and still submits

resolve_rl_train_data() only extracts when is_hf_dataset_path() is true; a local path passes through verbatim, and SkyRL's dataset wants a directory of task subdirs each holding instruction.md. The log says "No task directories or environments found; skipping" and the job burns a multi-node allocation training on nothing.

Fix Extract explicitly with scripts.datagen.extract_tasks_from_parquet, then pass the directory. The confirmation to look for is Found 3328 task(s) with 7 unique environment(s) — a skipped prebuild means the tasks are not wired.

Loud, but very late MoE policy construction needs SkyRL's ep extra

All eight vLLM engines load Qwen3.6 successfully — the expensive part — and then FSDP policy init dies in skyrl_train.models.layers.moe with ModuleNotFoundError: No module named 'torchtitan'. Grouped-GEMM MoE with the Torch expert-parallel backend requires TorchTitan, declared under SkyRL's ep extra, which the borrowed envs/rl-megatron lacked. This is exactly what killed 1141941.

Fix Install TorchTitan at a1fdd7e43694bbfeff5d6ad8ac738c067bb90d41 plus tomli and tyro into the actual RL venv. Gate on importing both torchtitan.distributed.expert_parallel and skyrl_train.models.layers.moe — a plain import skyrl_train is insufficient.

Looks like a hang A 90-minute "hang" that is a failed CUTLASS kernel build

On Qwen3-30B-A3B, vLLM 0.22 with moe_backend=auto selects a FlashInfer CUTLASS MoE path that JIT-compiles 183 nvcc units at engine start with --threads=1. The build failed at 182/183 and the worker went down; the engine sat in shm_broadcast until walltime.

Fix moe_backend="triton" — engine up in ~4 min. Related and opposite: a 30B Megatron job silent for 10+ minutes is usually just FlashInfer MoE autotuning. Do not call a big job wedged too early.

Startup stall Offline W&B still hangs when actors force mode="shared"

The driver says WANDB_MODE=offline, then model construction stalls ~90 seconds while per-node W&B actors attempt an online shared run. MarinSkyRL's distributed tracking path hard-coded mode="shared", ignoring the driver.

Fix Derive the mode once; in offline/disabled mode initialize only the local run and create no per-node actors. Verified corrected on 1141941.

Environment Cluster dotenv silently overwrites explicit launch paths

A generated Jupiter job started in another user's scratch tree and activated their Miniforge even though owned DCFT, SCRATCH and venv paths were supplied — hpc.set_environment and the generated sbatch sourced dotenv values after the caller's environment, treating site defaults as overrides.

Fix Dotenv entries are defaults only (${NAME:-default}), and RL jobs skip the generic cluster Conda activation. Regression-test the generated sbatch, not just the Python config.

Project-wide Never find or du on GPFS

Inode quota is the binding constraint, and caps are ~3M files for all users of a compute project — hitting it locks the project for everyone. Two cancelled Apptainer builds already took /p/scratch to 100% inode use.

Fix Unpack and build on ${LOCALSCRATCH:-${TMPDIR:-/tmp}} and atomically copy only completed SIFs to GPFS. Remove leftover temp trees single-threaded. Watch jutil project dataquota. This is the one failure mode that genuinely harms other users.

Expected A checkpoint appears despite a huge ckpt_interval

SkyRL always writes a final checkpoint and HF export at clean termination. Not a bug — just account for the disk. Relatedly, a WorkerCrashedError right after "Successfully saved model weights" is node memory pressure during save: check the artifacts before concluding the run lost work.

JURECA runs only the x86_64 sandboxes.

Training rollouts also use OpenCode, not Terminus-2. That began as a workaround for a known Terminus2 issue, but it removes a real confound: training against one interaction format and measuring under another is a train/eval mismatch. Same agent on both sides is strictly better science.

The allowlist trap this exposed

harbor_config.py builds AgentConfig(name=…, kwargs=…) through an allowlist of FieldMappings. Keys absent from that table are silently dropped — which is how strict_json_parser spent an entire workstream as dead configuration. Contract tests now verify the OpenCode fields actually arrive. Assume any new Harbor field is dropped until a test proves otherwise.

The pre-GRPO arm runs against the immutable staged checkpoint; the post arm against a selected HF export. The report must carry raw resolved counts and rates, the absolute percentage-point delta, per-task transitions, a paired-bootstrap 95% interval, and an exact McNemar p-value — not a bare delta. The model card's SWE-Bench score is not a baseline.

The baseline doubles as a harness check — with the threshold stated in advance

Compare our baseline against Qwen's published SWE-Bench Verified figure, not to reproduce it but to catch a broken harness before blaming the model. It is a band, not a reproduction: different scaffold, n=100 vs 500 (binomial SE ≈ ±5 pp), one attempt, no compaction. A gap under ~10 pp is indistinguishable from sampling plus harness differences. If we land more than ~15 pp below the published figure, stop and audit the harness.

The precedent: the gsm8k pass_at_1 ≈ 0.45 plateau was a format artifact, not math ability. Paired re-scoring of one generation pass showed strict@1024 = 41.6% vs flexible@4096 = 90.67% — the model answers in \boxed{N} and never emits ####. Formatting cost 37.7 points, truncation 11.3. A number that looks like capability is often the harness.
