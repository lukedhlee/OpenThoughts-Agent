# Weekly Goal - 2026-07-27

## Goal

Make Megatron a reliable replacement for FSDP2 on our Qwen3-30B-A3B GRPO runs on Jupiter — with safe checkpointing and a real speed comparison — and settle the open questions about how correct and how efficient our current setup actually is.

## Achieved

**Megatron is now a viable backend on Jupiter.**
- Validated the full train / generate / forward / weight-sync loop on 6 nodes.
- Got checkpoint save-and-resume working, including the full optimizer and LR-scheduler state (not just model weights), and fixed an unsafe default in how that state was stored.
- Fixed a memory spike on resume by freeing the loaded model before restoring the optimizer.
- Speed: **Megatron is ~1.36x faster overall and ~1.66x faster on the training step** than FSDP2 on GSM8K. GSM8K is generation-heavy, so this probably *understates* Megatron's advantage — longer-sequence workloads should favor it more.

**Our current runs were trustworthy — the setup was under-specified, not broken.**
- The `max_staleness_steps: 4` we were worried about turned out to be a red herring: it only affects the async trainer, and our runs use the synchronous one where staleness is always zero. So the runs were fully on-policy.
- We measured the real question — the gap between how vLLM and the trainer compute probabilities — and it's small (~3%). The correction for it (TIS) is cheap, so we're keeping it on for MoE runs. The heavier fix (router-replay / R3) buys essentially nothing here, so we're not building it.

**Settled the colocated-vs-disaggregated debate.**
- Disaggregated (splitting inference and training onto separate GPUs) is the clear winner for 30B-A3B on these GPUs. Colocation kept failing in different ways and doesn't fit in memory. The intuition that role-splitting was the right call held up.

**Answered whether we can use TP > 1 (tensor parallelism) on Jupiter.**
- Yes, it's possible, but we haven't actually run it in the RL loop yet. There are two known Jupiter-specific snags (a networking one that's already worked around in our configs, and a library-linking one with a known fix). This matters because TP > 1 is the main thing that could make colocation viable — it shards the model so no single GPU has to hold the whole thing.

## Doing

- Treat Megatron as usable for fixed-topology 6-node GSM8K runs on Jupiter.
- Keep TIS on for MoE runs; don't invest in router-replay unless a future long-context or larger-MoE run needs it.
- Stick with disaggregated as the default setup.

## Left

- Add guardrails so unsupported Megatron checkpoint modes fail early with a clear message, and document that resuming onto a different node count isn't supported.
- Add regression tests for the checkpoint fixes so they don't silently break.
- Look into whether weight-sync can be sped up — it's still a big chunk of each step.
- Run a fair long-sequence Megatron vs FSDP2 benchmark, since GSM8K undersells Megatron.
- Optionally, smoke-test TP > 1 on Jupiter to confirm the networking path works and potentially unlock colocation.
